# Relations as lines — design

**Date:** 2026-09-19
**Surface:** the node panel's Relations group
(`components/panels/RelationsGroup.tsx`, `components/panels/NodeRelationSections.tsx`,
`components/panels/AcceptancesSection.tsx`, `components/panels/BlockedByField.tsx`)

## The problem

Three separate complaints about the same region.

**`blocked_by` is filed with the fields that say what the record *is*.** It sits
in `NodeFields`' intro column, between the Product picker and the species'
authored fields — and on a decision it is somewhere else again, rendered by
`DecisionEditor` under "Context — why". But "what blocks this" is not a property
of the record; it is the record pointing at another record, which is the exact
definition the Relations group was built on. It is also the one field in that
column that is usually empty, so on most panels it is a labelled input occupying
two lines to say nothing.

**Every attach affordance in the group is a permanent, empty control.** Covers
carries an always-visible `AttachAnchorRow` — a species `Select` plus a search
field, two lines of chrome under a list that is frequently one row long.
Acceptances carries a ghost "Add" button that opens a `window.prompt`. Neither
costs nothing when unused, and they disagree with each other about what adding
looks like.

**Most of the graph's grammar has no edit path from a panel at all.** `calls`,
`displays`, `queries`, `supersedes`, `generates` and `impacts` can only be
authored by dragging a connection on a map. A reader looking at an API endpoint's
panel can see what it queries and has no way to say it queries one more thing.
`ConnectionsSection` flattens all of them into one undifferentiated "Connections"
list that names the counterpart's species in grey text on the right, which is
the *species*, not the relation — a view that calls an endpoint and a view that
an endpoint calls back read identically.

## The shape

Every relation becomes a **line**: its label, a `+` pushed to the right of that
same line, and its rows underneath. An empty relation is exactly one line — no
em-dash, no "None yet", no input. The `+` opens a combobox inline under the
heading; picking a node writes the edge, and a `×` on each row removes it.

```
Relations                                    [crit 2]
  Blocked by                                       [+]
    ◆ DEC-payments-vendor                          [×]
  Acceptances                                      [+]
    ◇ Cart totals update live                      [×]
  Calls                                            [+]
    ▣ POST /orders                                 [×]
  Called by                                        [+]
  Displays                                         [+]
    ▤ Order                                        [×]
  Impacted by                                      [+]
  Invocation
    ◈ Checkout flow
  References
    ↗ figma.com/…
```

Three sections stay read-only and keep their present shape: **Invocation**
(`composes` carries playlist ordering and `PlaylistEditor` owns that write),
**References** (`metadata.refs` are URLs, not nodes, so a node combobox is the
wrong control) and **Findings** (an audit result, not something a reader
authors).

## 1. The grammar table — `lib/utils/relation-lines.ts`

One module answers "what relation lines does a node of this species have?",
derived from `VALID_EDGE_SEMANTICS` in `@arkaik/schema`. Derived, not restated:
the connect dialog (`EdgeTypeDialog`) already reads that table, and a
hand-written second list of what may attach to what is a second chance for the
panel and the canvas to disagree about the graph model.

```ts
export interface RelationLine {
  /** `${edgeType}:${direction}` — "calls:out", "covers:in". Stable, sortable. */
  id: RelationLineId;
  edgeType: EdgeTypeId;
  /** Relative to the panel's node: does the edge leave it or arrive at it? */
  direction: "out" | "in";
  label: string;
  /** What a new counterpart may be, from the grammar. Never empty. */
  counterpartSpecies: SpeciesId[];
}

export function relationLinesFor(species: SpeciesId): RelationLine[];
```

**Labels** are one `Record<EdgeTypeId, { out: string; in: string }>`:

| Edge type | Outbound | Inbound |
|---|---|---|
| `calls` | Calls | Called by |
| `displays` | Displays | Displayed by |
| `queries` | Queries | Queried by |
| `covers` | Covers | Acceptances |
| `supersedes` | Supersedes | Superseded by |
| `generates` | Generated acceptances | Generated by |
| `impacts` | Impacts | Impacted by |

`covers:in` is "Acceptances", not "Covered by", because that is the heading the
section has carried since it existed and the word a reader of a view panel is
looking for. It is the one label that is not mechanically derived from the edge
type, and it is written down here rather than special-cased at the call site.

**`composes` is excluded from the table entirely.** A `composes` edge is half of
a relationship whose other half is `metadata.playlist.entries`, and writing one
without the other leaves the flow's order silently reconciled by
`journey-graph`'s "append the missing children" fallback. `PlaylistEditor` owns
that write. The exclusion is a named constant with this reason beside it, so the
next person to notice Composes is missing finds the answer instead of adding it.

**Order** is an explicit `RELATION_LINE_ORDER` array of line ids, not the
grammar's own order: covers lines first, then cross-layer, then decision links.
That is the per-species order the panel spec already used, and sorting by
`EDGE_TYPE_IDS` index would quietly reorder every panel the day an edge type is
appended to that enum.

What the table yields per species:

| Species | Lines (in order) |
|---|---|
| `view` | Acceptances · Calls · Called by · Displays · Impacted by |
| `flow` | Acceptances · Calls · Impacted by |
| `data-model` | Displayed by · Queried by · Impacted by |
| `api-endpoint` | Calls · Called by · Queries · Impacted by |
| `acceptance` | Covers · Generated by |
| `decision` | Supersedes · Superseded by · Generated acceptances · Impacts |

Plus **Blocked by** on every species, which is not an edge and so not in this
table — see §4.

Two of these lines show information no panel has ever shown: **Impacted by** on
the four species a decision may impact, and **Generated by** on an acceptance.
Both are facts already in the graph with no surface reading them, and both are
the kind of fact a reader of that record wants: a view that a decision impacts
should say which decision.

`api-endpoint`'s `calls:out` is the one line whose `counterpartSpecies` has two
entries (`api-endpoint`, `view`) — the grammar admits both, so the combobox
searches both and offers a create row per species.

## 2. The line primitive — `components/panels/RelationLine.tsx`

`RelationLine` wraps `PanelSection`. That component's `action` slot is already
documented as "a ghost Button pushed to the right of the heading … hoisted here
so the next section that needs one does not re-derive the `justify-between`
row", which is exactly the `+`. Wrapping it rather than re-implementing the row
means the panel gutter, the `h4`-inside-a-`PanelGroup` heading semantics and the
section spacing all come free and stay in one place.

```ts
interface RelationLineProps {
  label: string;
  /** The rows, already rendered. Absent means the line is heading-plus-`+`. */
  children?: ReactNode;
  /** Absent means read-only: no `+`, and the caller drops the line when empty. */
  add?: {
    counterpartSpecies: SpeciesId[];
    /** Ids already on this line — excluded from the list, never offered twice. */
    excludeIds: readonly string[];
    onSelect: (nodeId: string) => void | Promise<void>;
    onCreate?: (species: SpeciesId, title: string) => void | Promise<void>;
    /** Blocked by only — see §4. The row shown when nothing matches. */
    freeText?: { render: (query: string) => ReactNode; onCommit: (text: string) => void };
  };
}
```

The `+` is a toggle carrying `aria-expanded` and an `aria-label` naming its line
("Add to Calls"), so two open panels' `+` buttons are distinguishable to a screen
reader. Open, it reveals a `Combobox` in its `inline` variant directly under the
heading — inline rather than a popover because the panel body already scrolls and
a floated list inside it needs portalling to escape the scroll container, which
is a second problem to solve for no gain in a region this narrow.

### Generalising `NodeSearchCombobox`

`NodeSearchCombobox` takes `species: "view" | "flow"` — one species, and only
those two. It becomes `species: SpeciesId[]`, with:

- the candidate filter matching any of them,
- `onCreate` gaining the species: `(species: SpeciesId, title: string) => …`,
- one create row per admissible species when the query matches no existing title
  ("Create view “X”", "Create flow “X”"), collapsing to the current single row
  when there is only one species,
- the placeholder and `aria-label` naming the set rather than the one species.

Two call sites are simplified by this rather than merely migrated:

- **`AttachAnchorRow` drops its `Select`.** The View/Flow select existed only
  because the combobox could search one species at a time; with two species in
  one list it is a control asking a question the search result already answers.
  (The playlist editor's Add-step popover reached this conclusion first, and its
  docblock says so.)
- **`AcceptancesSection` drops its `window.prompt`.** Creating an acceptance for
  an anchor becomes the combobox's create row, which also means the section can
  finally *attach an existing* acceptance — something no surface offered.

## 3. Writes — one capability, mirroring `intake`

A single `relations?: NodeRelations` prop, threaded exactly as `intake` is
(`ProjectPanels` → `NodeDetailPanel` → `RelationsGroup`), for the reason
`AcceptanceIntake`'s docblock gives: it is one capability, and threading three
callbacks through three layers is three chances for a surface to end up
half-wired. A page whose panels are read-only passes none, and no `+` or `×`
appears anywhere.

```ts
export interface NodeRelations {
  /** Write one edge. A no-op if it already exists. */
  link(source: Node, target: Node, edgeType: EdgeTypeId): Promise<void>;
  /** Remove one edge by id. */
  unlink(edgeId: string): Promise<void>;
  /**
   * Create the counterpart *and* link it, as one write. Resolves to the new
   * node, or `null` when the title was blank.
   */
  linkNew(node: Node, line: RelationLine, species: SpeciesId, title: string): Promise<Node | null>;
}
```

The rules live in `lib/utils/node-relations.ts` as pure functions over
`MutationOp[]` and are asserted there; `lib/hooks/useNodeRelations.ts` turns a
plan into a write and keeps the surface's node and edge state in step. That is
the split `useAcceptanceIntake` and `lib/utils/acceptance-intake.ts` already use,
and the reason is the same: the rules are testable without a store.

`link` resolves direction from the line, not from argument order at the call
site — a `direction: "in"` line writes `counterpart → node`. The plan asserts
`isValidEdgeSemantic` before emitting and throws otherwise, so an inbound line
can never produce an edge the importer would reject.

### `covers` is the deliberate exception

Both covers lines keep the write paths they have today — `intake.attach`,
`intake.detach`, `intake.createAnchor` and `onCreateAcceptanceForAnchor` — and
do **not** go through `relations`. A covers edge is not just an edge: attaching
one can empty an acceptance's derived product membership (announced by
`AttachAnchorRow`'s triage warning), and a node created in that gesture inherits
the acceptance's product. A generic edge write knows none of that, and two
writers for one edge type is precisely the disagreement the group's existing
docblocks spend paragraphs preventing.

So the boundary is written down in both modules: **covers edges are intake's,
every other edge is `relations`'.** What the covers lines adopt from this work is
the `RelationLine` *look*, not its write path.

## 4. Blocked by

`metadata.blocked_by` is a single string that may name a node or say anything at
all ("waiting on legal"). It becomes a line in the group like any other, and it
is **first** — it is the relation that changes how the rest of the record reads,
since a node's status means something different when something blocks it.

- **Empty:** heading plus `+`.
- **Set to a node id this panel can resolve:** one `EntityRow`, which navigates
  and copies its id like every other row in the group.
- **Set to anything else:** one row of plain text.
- **`×`** clears the key — `withBlockedBy(base, null)`, which already owns the
  "empty means *absent*, never `blocked_by: ""`" rule.
- **The combobox** searches every species, and once the query matches no node
  title a last row commits it as free text ("Blocked by “waiting on leg”"). That
  is the `freeText` slot in `RelationLineProps`, and it is the only line that
  uses it: nothing a bundle can hold today stops being authorable.

Because it is single-valued, the `+` is present only while it is empty.

**Two renderers collapse into one.** `NodeFields` renders `BlockedByField` for
five species and `DecisionEditor` renders its own for the sixth, under "Context —
why". Both go. The `metadataRef` prop exists solely because `DecisionEditor`'s
non-optimistic `onUpdate` made this field a fifth writer racing its siblings over
`node.metadata`; with the field out of that editor there is no shared write base
to join, and the prop goes with it.

## 5. What this forces in `RelationsGroup`

Its "renders nothing when every child would" rule is restated, not deleted. The
rule exists because "a bar over seven empty sections promises a reader something
to open and then opens onto nothing", and that promise is still worth keeping —
but the test changes, because with a write capability in hand every line has a
`+` and so is never truly empty:

> The group renders when any line has rows, **or** when the surface can write.

And the corollary, which is what the "heading plus `+`" shape costs on a
read-only surface: **an empty line is dropped when there is no `+` to put on
it.** A bare label with nothing underneath is an empty state, which is the thing
the group's existing flags exist to avoid. Writable panels therefore show the
full grammar, including the lines with nothing in them; read-only panels show
only what exists.

The per-child `has*` flags are replaced by one pass over `relationLinesFor(node.species)`
that resolves each line's rows, plus the four flags the non-edge children still
need (`hasRefs`, `hasFindings`, `hasInvocation`, blocked-by). `decisionConnections`
and `crossLayerConnections` are subsumed by that pass: the first disappears, and
the second stays only as the map/canvas helper it also is — checked, not assumed,
before removing anything from it.

## 6. Testing

- **`relation-lines.ts`** — the table is asserted directly: every species' line
  list and order, every line's `counterpartSpecies` against
  `VALID_EDGE_SEMANTICS`, `composes` absent, and a guard that every `EdgeTypeId`
  has both labels so adding an edge type to the enum fails here rather than
  rendering `undefined` as a heading.
- **`node-relations.ts`** — plans for out and in directions, the already-linked
  no-op, `linkNew` with a blank title, and the `isValidEdgeSemantic` refusal.
- **Panel semantics** — `tests/app/panel-semantics.test.js` asserts the heading
  outline, and the number of `h4`s in the group roughly doubles. It needs
  updating in the same part that changes the count, not after.
- **Product scope** — `tests/app/product-scope.test.js` reads panel *source
  text*, so relocating this JSX fails it as a shape violation rather than as a
  relocation. Expect it in parts 2 and 4 and read the assertion before editing
  it: the point of that suite is that the product rules stay reachable, and an
  assertion loosened to make a move pass is the rule going quiet.

## 7. Shipping — a stack of four parts

Ordered by dependency, with the move separated from the rewrite.

1. **The grammar table.** `lib/utils/relation-lines.ts` and its tests. Pure
   logic, nothing on screen, nothing imports it yet.
2. **The line primitive.** `RelationLine`; `NodeSearchCombobox` generalised to
   `SpeciesId[]`; Covers, Acceptances and Decision links adopt the new look.
   `AttachAnchorRow` loses its `Select`, `AcceptancesSection` loses its
   `window.prompt`. A reshape of what exists — no new writable relation.
3. **Edge authoring.** `node-relations.ts`, `useNodeRelations`, the prop threaded
   through; Connections splits into its per-relation lines; every writable line
   gains `+` and `×`; `RelationsGroup`'s emptiness rule is restated.
4. **Blocked by moves.** Out of `NodeFields` and `DecisionEditor`, into the group
   as its first line, with the free-text combobox row. `metadataRef` is removed.

Each part lints, typechecks and passes the suite on its own.

## 8. Docs

`docs/graph-model.md` § Edge Types gains a sentence: edges are authored from the
maps by drawing a connection, and from a node panel's Relations group, both
constrained by the same `VALID_EDGE_SEMANTICS` table — except `composes`, which
only the playlist editor writes.

## Out of scope

- Reordering rows within a line. Edges are a set; only `composes` is ordered, and
  that is the playlist's.
- Editing an existing edge's *type* in place. Remove and re-add.
- `References`, which needs a URL control, not a node combobox.
- Making Invocation writable, which needs a playlist write alongside the edge.
